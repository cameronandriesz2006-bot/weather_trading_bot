# B5 + B6 — atomic execution path, API limits, VPS placement

Research run 2026-08-02. No money at risk, no authenticated calls, no service touched.
All on-chain reads were `eth_call` / `eth_getLogs` against public Polygon RPCs.

Two findings dominate everything else in this document:

1. **This machine cannot place orders.** Singapore is a restricted jurisdiction on both the
   frontend *and* the API. `GET https://polymarket.com/api/geoblock` from this box returns
   `{"blocked":true,"country":"SG"}`. Go-live from here is impossible regardless of what the
   arb is worth. (§B6.2)
2. **Legging risk is asymmetric, and the SHORT side has an atomic on-chain exit that the BUY
   side does not.** `NegRiskAdapter.convertPositions` turns NO tokens on *m* buckets into
   `(m−1)` USDC plus YES on the complement, in one transaction, immediately, with no
   protocol fee on these markets (`feeBips = 0`, read on-chain). At `m = 11` that is a
   complete unwind to `$10` cash with no wait for resolution. A **full 11-leg YES set has no
   such path and is provably locked to resolution.** (§B5.1, §B5.2)

# B5 — is there an atomic path?

## B5.1 — What `convertPositions` does, and can it replace/de-risk the SHORT leg?

```solidity
/// @notice Convert a set of no positions to the complementary set of yes positions plus
///         collateral proportional to (# of no positions - 1)
function convertPositions(bytes32 _marketId, uint256 _indexSet, uint256 _amount) external
```
(`NegRiskAdapter.sol` L237–L359; `_indexSet` is a bitmask over question indices, LSB = index 0.)

Mechanically, for an index set `S` of size `m` on a market with `n` questions, amount `a`:

- your `NO_i` for `i ∈ S` are transferred to `NO_TOKEN_BURN_ADDRESS` — permanently burned
  (L315–L328, comment: *"these must never be redeemed"*);
- for each `j ∉ S` the adapter mints unbacked wrapped collateral and splits it, keeping the
  resulting `NO_j` (also burned) and handing you `YES_j` (L277, L296–L308, L344–L356);
- you receive `(m − 1) · a` collateral (L333–L342);
- fee = `a · feeBips / 10_000`, taken from both the collateral and the YES legs — **zero here**.

**Value identity.** `NO_i ≡ Σ_{j≠i} YES_j`, so the operation is value-neutral: you pay
`Σ_{i∈S}(1−p_i)` worth of NOs and get `(m−1)` cash + `Σ_{j∉S} p_j` of YES, which sums to the
same. What changes is *form* and *timing*.

**Does it replace multi-leg SHORT execution?** No — you still have to buy each NO leg
one at a time on the book, and pay the taker fee on each. It does not remove entry legging
risk.

**Does it de-risk them? Substantially, yes — in three ways:**

1. **Instant settlement.** Short-the-board (`m = n = 11`) converts to a flat `$10` USDC in a
   single transaction. No wait for resolution, no redeem step. The capital recycles in one
   Polygon block, not one day. This is the difference between the test plan's `$2.81/day per
   $100` column and its `$14/day` column — **for the short side that column is real**.
2. **Partial fills are benign, not catastrophic.** If you only get NO on `k` of 11 legs, you
   convert with `indexSet` = those `k` and receive `(k−1)` cash + YES on the other `11−k`.
   You are never holding a set that pays `$0`; you hold a defined position worth exactly what
   you paid at mid. This is the opposite of the buy-the-board failure mode.
3. **It compresses position count**, which matters for redeem gas later.

**This is not theoretical — it is in active use on our exact boards.** Scanning
`PositionsConverted` logs on the adapter over the last ~20 000 blocks (~11 h) found **4 192
conversions**, of which 130 had an 11-bit index set. One of them,
[`0x6d0a937e92fa680fc155f7e8f3943bc2961a6034fd377f63c55f019d92af6905`](https://polygonscan.com/tx/0x6d0a937e92fa680fc155f7e8f3943bc2961a6034fd377f63c55f019d92af6905),
is `indexSet = 2047` (all 11 bits) on marketId `0xccfa58a5…8300`, which resolves via Gamma to
**"Highest temperature in Chengdu on August 3?"** — a daily-temperature board of exactly the
kind the scanner sweeps. Amount converted: **5.17 shares** (min order size is 5). Somebody
else is already running this trade at micro size.

## B5.2 — Buy-side early merge: can a complete 11-leg YES set become ~$1 before resolution?

**No. Definitively no, and not because the docs are silent — it is arithmetically impossible
with the operations the adapter exposes.**

The adapter offers exactly four position primitives, all in `NegRiskAdapter.sol`:

| op | signature | effect per unit |
|---|---|---|
| split | `splitPosition(bytes32 conditionId, uint256 amount)` | −1 collateral, +1 `YES_i`, +1 `NO_i` — **one condition at a time** |
| merge | `mergePositions(bytes32 conditionId, uint256 amount)` | −1 `YES_i`, −1 `NO_i`, +1 collateral — **one condition at a time** |
| convert | `convertPositions(bytes32 marketId, uint256 indexSet, uint256 amount)` | −`NO_i ∀i∈S`, +`YES_j ∀j∉S`, +(|S|−1) collateral |
| redeem | `redeemPositions(bytes32 conditionId, uint256[] amounts)` | post-resolution only |

Note that split and merge take a **single `conditionId`**, and each of the 11 buckets is its
own binary CTF condition (proved in the setup section: 11 distinct `conditionId`s). Merging
requires `YES_i` **and** `NO_i` of the *same* condition. A full YES set contains no NOs, so
there is nothing to merge against.

**Proof that no combination works.** Let `s_i, m_i ≥ 0` be split/merge amounts on question
`i`, and `c_S ≥ 0` the amount converted with index set `S`. Then

```
ΔYES_i  = s_i − m_i + Σ_{S : i∉S} c_S
ΔNO_i   = s_i − m_i − Σ_{S : i∈S} c_S
ΔYES_i − ΔNO_i = Σ_{all S} c_S  =: C ≥ 0      (same for every i)
```

To dispose of a full YES set we need `ΔYES_i = −1` for all `i`, and we cannot end short of
NO, so `ΔNO_i ≥ 0`. That forces `C = −1 − ΔNO_i ≤ −1 < 0`, contradicting `C ≥ 0`. ∎

The intuition: the only way to destroy a YES token is to merge it against a NO token, and the
only way to obtain a NO token is to buy it or to split (which costs the dollar you were trying
to recover). `convertPositions` runs strictly NO → YES; there is no YES → NO direction.

**Consequences for the buy-the-board arb:**

- Capital is **locked to resolution.** For daily-temperature boards that is ≤ ~24–36 h, so the
  recycle rate is ~1/day and the test plan's **`$2.81/day per $100` column is the correct one
  for buy-the-board.** The `$14/day` column does not apply to it.
- Exit cost is one `redeemPositions` on the *winning* condition only — the 10 losing YES
  tokens are worthless and need no transaction. Measured redeem gas ≈ 412 k ≈ **$0.011**.
- The only pre-resolution exit is to **sell the legs back on the book**, which pays a second
  round of taker fee on 11 legs and is almost certainly negative against a ~1 ¢ edge.
- Interesting corollary: because minting a full set costs exactly `$1` (see B5.4), the
  buy-the-board arb is *bounded above* by the mint — nobody rational sells you the board for
  much under `$1` when they can create it for `$1`. That is a structural reason the buy-side
  edge is thin, independent of competition.

**Caveat, stated explicitly:** the newer Combos stack has a *Collateral Return Router*
(`0x12121212006e4CD160D18e3f00711DA5c3372600`) that decomposes offsetting positions back to
pUSD before resolution
(<https://docs.polymarket.com/trading/combos/collateral-return>). Our boards are on the
**USDC.e / v1 adapter** stack (verified above), so it does not apply today. If Polymarket
migrates the weather boards to pUSD/PositionManager, this answer should be re-checked — it is
the one thing that could change it.

## B5.3 — Atomic multi-market execution at the exchange layer?

**No. Best-effort per-order is the only mode available to a taker.** Three independent
confirmations:

1. **API.** `POST /orders` accepts **1–15 signed orders**, and the docs say *"Orders are
   processed in parallel"*; each order in a batch is accepted or rejected **independently**
   (<https://docs.polymarket.com/api-reference/trade/post-multiple-orders>,
   <https://docs.polymarket.com/trading/place-orders>). There is no batch-level FOK.
2. **Order semantics.** `orderType ∈ {GTC, FOK, GTD, FAK}` is a **per-order** field in the
   `SendOrder` schema. `FOK` = "fills the entire order immediately or does not fill any of
   it" — that is all-or-nothing for *one* order on *one* token, not across a batch.
3. **Contract.** In `Polymarket/ctf-exchange`, `fillOrder`, `fillOrders(Order[], uint256[])`
   and `matchOrders` are all `onlyOperator` (`src/exchange/CTFExchange.sol` L61, L68–71,
   L82–87). The operator *can* settle many orders in one transaction, but that is Polymarket's
   matcher, not a surface a taker can drive. You cannot submit "fill these 11 or none".

One near-miss worth flagging: the **Combos / RFQ** product does execute a multi-leg position
atomically (<https://docs.polymarket.com/trading/combos/overview>). It is not usable here for
two reasons — the *Requesters* integration is marked **"Coming Soon"** (only the market-maker
side is documented), and a Combo collapses its legs into a single YES/NO position, which for
11 *mutually exclusive* buckets is not the instrument we want.

**The one genuinely atomic multi-market primitive available to us is `convertPositions`** — and
it operates on positions you already hold, not on order execution. Hence the asymmetry in
B5.1/B5.2: you can atomically *exit* a short basket; you cannot atomically *enter* anything.

**Practical implication for A2:** the best achievable entry is a single `POST /orders` call
carrying all 11 legs as FOK (or FAK) orders. That is one network round trip and one
rate-limit charge, so all 11 hit the matching engine within a few ms of each other — but they
match independently, so A2 must still model partial sets. What the batch buys you is that the
11 legs are exposed to *one* round trip of staleness, not eleven.

## B5.4 — Is minting a full set ever cheaper/safer than taking 11 asks?

**Minting a full 11-leg YES set costs exactly `$1.00` + gas, with zero taker fee and zero
legging risk**, via two calls:

1. `splitPosition(conditionId_k, a)` on any single bucket `k` — pay `a` USDC, receive `YES_k`
   and `NO_k`;
2. `convertPositions(marketId, 1 << k, a)` — burn `NO_k`, receive `YES_j` for all `j ≠ k`,
   collateral out `= (1−1)·a = 0`.

Result: `YES_i` for all 11 buckets, total outlay exactly `a`.

**So it is never a cheaper *entry* for buy-the-board.** The whole premise of that trade is
paying **under** `$1`; the mint pays exactly `$1`. It is a price ceiling, not an opportunity.
Where it *is* the better route:

| scenario | verdict |
|---|---|
| ask-sum barely `< $1` (say `$0.995`), 11 taker fees ≈ 1.5–3 ¢ | **mint loses too** — but so does taking the asks. Both are negative; the fee already kills it. The mint at least has no legging risk, but there is no profit to protect. |
| you need a full set as *inventory* to make markets on | **mint wins** — `$1` flat, no taker fee, no legging risk, 2 txs ≈ $0.03–0.05 gas |
| short-the-board (`Σ NO asks < $10`) | **convert wins decisively** — buy the 11 NOs, one `convertPositions(marketId, 0x7FF, a)` returns `$10` immediately (measured 896 k gas ≈ **$0.021**) |
| you are holding a partial NO basket after a failed leg | **convert is the unwind** — returns `(k−1)` cash + YES on the complement, one tx |

**Measured gas** (Polygon, 2026-08-02, POL @ $0.0723, base fee 335–378 gwei; real transactions
pulled from `eth_getLogs` on the adapter and priced from their receipts):

| operation | gas used | cost | note |
|---|---|---|---|
| `convertPositions`, 11-of-11 (`indexSet=2047`, 0 YES splits) | 896 212 | **$0.021** | tx `0x6d0a937e…6905`, an actual 11-bucket weather board — single observation |
| `convertPositions`, partial (4–8 YES splits) | 1.35 M – 5.0 M | $0.03 – $0.13 | gas scales with the number of YES legs the adapter must split |
| `redeemPositions` | 368 k – 601 k, median 412 k | **$0.011** | via a proxy/batch redeemer |
| `splitPosition` / `mergePositions` | 616 k – 673 k median | ~$0.015 – $0.017 | **caveat:** most samples had `to =` the NegRisk CTF Exchange, i.e. they were emitted inside a *match* transaction, so this is an upper bound that includes matching work, not a clean standalone split/merge |

All figures include Polymarket proxy-wallet overhead (`to =` Deposit Wallet Factory
`0x00000000000Fb5C9ADea0298D729A0CB3823Cc07` or a user proxy), which is what our own
transactions would also carry. Gas price was elevated (335–378 gwei) during the sample.

Compared with the test plan's assumed **$0.02 per position**, the real numbers are: one
convert for the whole board ≈ $0.021, one redeem ≈ $0.011. **Per-board, not per-leg.** That is
materially cheaper than the plan assumes, and it is the concrete answer B4 was looking for.

**Gasless option:** the Relayer API (`POST /submit`, gas-sponsored, `{to, data, proxyWallet,
type: SAFE|PROXY}`) will submit arbitrary transactions on your behalf, so a convert can be
fired without holding POL. It is async — you get a `transactionID` and poll `GET /transaction`
for the hash — and it is rate limited to **25 requests / minute**
(<https://docs.polymarket.com/api-reference/relayer/submit-a-transaction>,
<https://docs.polymarket.com/api-reference/rate-limits>). 25/min is a real ceiling on a
convert-and-recycle loop; direct Polygon submission avoids it.

# B6 — practical API limits + VPS placement

## B6.1 — CLOB API limits

**Minimum order size: 5 shares.** Confirmed two ways for a live weather bucket
(`GET https://clob.polymarket.com/markets/0x260ccf80…4fe4` → `"minimum_order_size": 5`; Gamma
`orderMinSize: 5`). This is per market and should be read, not hard-coded.

**Tick size: per market, and it moves.** The Toronto board carried `0.001` on the tail buckets
and `0.01` on the mid buckets on the same day. Tick tightens as price approaches the extremes,
and the market websocket emits a `tick_size_change` event ("Market tick size update when price
approaches limits"). Read it from `GET /tick-size?token_id=…` or the market object; a stale
tick produces `Price (100) breaks minimum tick` rejections.

**Rate limits — two independent layers**
(<https://docs.polymarket.com/api-reference/rate-limits>,
<https://docs.polymarket.com/api-reference/trading-rate-limits>):

*Cloudflare, per IP:*

| endpoint | limit |
|---|---|
| `POST /order` | 5 000 / 10 s burst, 120 000 / 10 min sustained |
| `POST /orders` | 2 000 / 10 s burst, 21 000 / 10 min sustained |
| `DELETE /order` | 5 000 / 10 s burst |
| `/book` | 1 500 / 10 s · `/books` 500 / 10 s |
| Relayer `/submit` | **25 / 1 min** |

*Per-signer token bucket (new; warning-mode from 2026-07-24, enforcement date TBA):*

| tier | order rate | order burst | cancel rate | cancel burst |
|---|---|---|---|---|
| **Standard** (us) | 40 tok/s | **60** | 80 tok/s | 120 |
| Silver ($100k/30d) | 200 | 300 | 400 | 600 |

`POST /orders` costs **one token per order in the batch**. A batch is admitted only if the
bucket holds enough tokens for *every* entry, else the whole request is rejected.

**Can 11 orders land inside ~100 ms? Yes, comfortably — and not by racing.** Put all 11 in a
single `POST /orders`: 11 tokens out of a 60-token Standard burst, one HTTP round trip, and
they reach the matching engine together. Sustained, the Standard tier supports ~3.6
eleven-leg boards per second — far above the ~1 hit/hour this strategy actually generates.
**Rate limits are not the binding constraint.** Geography and latency are.

**Batch endpoint: `POST /orders`, max 15 orders per call.** 11 fits in one call with room to
spare. Orders may span different markets (the schema is just an array of signed orders, each
with its own `tokenId`). Accept/reject is per order.

**Order types: `GTC`, `GTD`, `FOK`, `FAK`** (`SendOrder.orderType` enum, default `GTC`). Also
per order: `postOnly` (GTC/GTD only — the maker path, which pays 0 fee and earns the 25 %
rebate) and `deferExec` ("Whether to defer execution", default false). **`deferExec` is
undocumented beyond that one line.** It is the only field in the schema that *might* imply
deferred/grouped execution and it is worth a direct question to Polymarket, but I will not
guess at its semantics.

`GTD` orders expire one minute before their stated expiration as a security threshold, so the
minimum useful lifetime is ~2 minutes (expiration ≥ 3 min out).

## B6.2 — Auth chain, KYC, geo — and the blocker

**Auth chain** (<https://docs.polymarket.com/getting-started/api>):

1. **L1** — the wallet signs an EIP-712 `ClobAuth` payload → `POST/GET /auth/api-key` (or
   `/auth/derive-api-key`) with headers `POLY_ADDRESS`, `POLY_SIGNATURE`, `POLY_TIMESTAMP`,
   `POLY_NONCE` → returns `{apiKey, secret, passphrase}`.
2. **L2** — every private request carries `POLY_ADDRESS`, `POLY_API_KEY`, `POLY_PASSPHRASE`,
   `POLY_TIMESTAMP` and an HMAC-SHA256 `POLY_SIGNATURE` over the request.
3. Order placement needs **both**: L2 authenticates the request, and the order itself carries
   a separate EIP-712 wallet signature. `signatureType`: `0 = EOA`, `1 = POLY_PROXY`,
   `2 = POLY_GNOSIS_SAFE`.

**KYC: not required to trade via the API.** The only KYC/KYB gate found in the docs is for
*direct co-location* in `eu-west-2`.

**Geo — this is the blocker.**
<https://docs.polymarket.com/api-reference/geoblock> defines three groups. **Singapore (SG) is
in the "Close-Only on Frontend *and* API" group** — existing positions can be closed, **no new
orders**. Measured from this box:

```
GET https://polymarket.com/api/geoblock
→ {"blocked":true,"ip":"45.76.179.243","country":"SG","region":""}
```

**This machine's region is not viable.** Every downstream item — C7 signing dry run, C8
end-to-end latency, D10–D13 — is unreachable from here. This should be promoted to the top of
the test plan: it gates Tier C entirely, and it is free to fix (a $6/mo VPS) but impossible to
work around.

Restricted groups, condensed:

- **OFAC, fully blocked:** IR, SY, CU, KP, UA-43, UA-14, UA-09.
- **Close-only on frontend *and* API** (no new orders): AU, BY, BE, BI, BR, CA-BC/ON/AB/QC,
  CF, CD, ET, **FR**, **DE**, IQ, **IT**, LB, LY, MM, NI, **PL**, RU, **SG**, SO, **SK**, SS,
  SD, TW, TH, **GB**, **US**, UM, VE, YE, ZW.
- **Close-only on frontend only — API not restricted:** **IE, JP, MT (sports only), NL**.

Note the trap: **GB is API-blocked**, so a London VPS — physically closest to their servers —
is not usable.

> **Compliance note, stated plainly:** geoblocking is enforced on the *IP*. Choosing a
> non-restricted hosting region is a latency decision. If the account holder is themselves
> resident in a restricted jurisdiction, using a VPS to place orders is a Terms-of-Service
> violation regardless of where the packets originate, with account/funds risk attached. That
> is a decision for the user, not something this report resolves.

   the *CLOB order endpoint itself* enforces geo identically is **not verifiable without
   authenticated credentials** — the first real test of that is C7.

**Why this matters more than it looks.** The shadow probe already showed arrival value decaying
hard inside 0.7 s. Our current round trip is 0.17 s *one way to acknowledgment*, so a
scan→decide→submit cycle from Singapore burns a large fraction of the window before an order
is even accepted. From Amsterdam the same cycle costs ~15 ms. **C8 ("real end-to-end latency")
should not be run from this machine at all — it would measure the VPS choice, not the
strategy.**

## B6.4 — Websocket market-data feed

**Yes, and it works from here today.** `wss://ws-subscriptions-clob.polymarket.com/ws/market`
(<https://docs.polymarket.com/api-reference/wss/market>,
<https://docs.polymarket.com/market-data/realtime-data>).

Subscribe with `{"assets_ids": [...], "type": "market"}`; optional `initial_dump` (default
true), `level` ∈ {1,2,3} (default 2), `custom_feature_enabled` (adds `best_bid_ask`,
`new_market`, `market_resolved`). Events: `book` (full snapshot), `price_change`,
`last_trade_price`, `tick_size_change`. Application-level heartbeat: send the text frame
`PING` every 10 s, server replies `PONG` (this is *not* a protocol-level ping).

**Live probe from this box**, subscribing to all 22 token ids (11 buckets × YES/NO) of
`highest-temperature-in-kuala-lumpur-on-august-2-2026`:

- connect (TLS + WS handshake): **399 ms**; first message at **885 ms**
- **2 917 frames in 25 s ≈ 117 messages/sec for a single board** — 24 `book` snapshots,
  2 909 `price_change`, 1 `last_trade_price`
- steady-state `PING`/`PONG` RTT: **160 ms median**

**No documented cap on subscribed asset ids, no documented message-rate throttle** for the
market channel. The CLOB WS is not listed in the rate-limits page (only the Perps WS is).
Absence of a documented limit is not proof there is none — treat ~140 boards × 22 tokens
≈ 3 000 subscriptions as unproven until tried.

**Implication:** the scanner's 2 s polling loop is leaving most of the signal on the floor.
At ~117 msg/s per board the book is changing continuously between sweeps, and the WS delivers
each change as it happens rather than up to 2 s late. Combined with the VPS move, the
detection path goes from *up to 2 s stale + 174 ms to react* to *~15 ms stale + ~15 ms to
react* — roughly two orders of magnitude, against a value that the shadow probe shows decaying
inside 0.7 s.

## What this changes in the test plan

1. **New Tier-0 blocker: the box is geo-blocked.** Nothing in Tier C or D is executable from
   Singapore. Fix = one VPS in Amsterdam or Dublin, ~$6/mo, plus a `geoblock` check.
2. **A2 (legging simulation) should be split by direction.** Buy-the-board and
   short-a-subset now have provably different risk profiles: a partial buy-set is an unhedged
   directional bet with a `$0` worst case, while a partial short-set converts cleanly to
   cash + a defined YES basket. Simulating them under one model would understate the buy side
   and overstate the short side.
3. **The capital question is answered, and it splits.** `$14/day per $100` is achievable for
   **short-a-subset** (convert recycles in one block for ~$0.021). `$2.81/day per $100` is the
   correct and unimprovable figure for **buy-the-board** (locked to resolution — proved).
4. **B4's gas assumption was pessimistic and mis-shaped.** Real cost is ~**$0.021 per board**
   to convert and ~**$0.011 per board** to redeem — per *board*, not per *position*, so the
   plan's `$0.02 × 11` framing overstates it by roughly an order of magnitude.
5. **Someone else is already doing the short-side trade** at ~5 shares on these exact weather
   boards. That is both validation that the mechanism works and a warning about who we are
   racing — from 174 ms away.
