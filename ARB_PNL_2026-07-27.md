# negRisk arb — "what if we only took the profitable trades?" (2026-07-27)

**Status: results to be audited. Do not act on these numbers until they are.**

This supersedes the *framing* of `AUDIT_2026-07-26_negrisk_arb_VERDICT.md`, not its findings.
That verdict's mechanics (fee is real, identity is sound, capacity is capped) all still hold.
What changed: the verdict answered "is this a >$50/day business worth a 2–3 week build?" and said
no. The question actually being asked is **"does this make consistent daily profit on small
capital?"** — and on 15.4h of fee-aware data the answer looks like yes. The verdict's own
estimate ("single-digit to low-double-digit $/day") came off an 18-minute sample and is too low.

## Reproduce

```bash
python3 -m backend.data.negrisk_arb_pnl --until 2026-07-27T05:07:00+00:00
python3 -m backend.data.negrisk_arb_pnl --until 2026-07-27T05:07:00+00:00 --gas 0.024
```

Source log `logs/negrisk_arb.jsonl` (not in git — 5.2MB, still growing). The `--until` flag
pins the window so a growing log reproduces these exact numbers.

**Provenance of the log is clean.** `negrisk-arb.service` started 13:41:02 with
`negrisk_arb_scan.py` written 13:40:52, working tree clean at `ec955b4`, **0 restarts** for the
whole window — so every row was produced by the post-fee-fix, post-`board_sanity` code. 0 sanity
failures logged; 0 rows non-positive; 0 rows below the 5-share order minimum.

## Method

The scanner writes a `board` row **only** when a board is net-of-fee profitable at real book
depth. So every row is already a trade we would have taken. Turning observations into executions:

- **One execution per standing mispricing.** Consecutive profitable sweeps on one board are one
  mispricing, not N. Grouped into episodes; gap > `--episode-gap` (default 300s) starts a new one.
- **Credited at arrival**, never at peak — you cannot trade a price you only see in hindsight.
- **Left-censored stock dropped** — episodes already standing within 120s of scanner boot are a
  one-time stock, not flow (worth only $0.05 here; it mattered far more in the gross-phase log).

## Audit targets — where I'd attack this first

Ranked by how much they could move the answer.

1. **FILL REALISM — entirely untested, and it is the whole thing.** Every number above assumes
   we get filled at the price the scanner scored. These are top-of-book paper prices from a
   snapshot. The trade carrying 60% of P&L existed for ~2 seconds. Nothing here has been checked
   against whether an order would actually have been taken. This is the same untested half that
   killed Edge-2 — and it is the one number that would make this real.
2. **The tail is n=1.** One flash in 15.4h drives the headline. It cannot be distinguished from a
   one-off at this sample size. If Milan doesn't recur, this is a $19–25/day strategy net of gas.
   Only more data settles it (~11× sample in a week).
3. **Legging risk is unpriced.** The arb pays only if all 11 legs fill. A partial fill leaves an
   incomplete set that can pay **$0** — one botched fill (~−$10) erases ~320 median trades at
   $0.031. No model of this exists anywhere in these numbers.
4. **`k` depth-honesty.** The Milan trade claims k=93.21 shares across 11 legs. The scanner walks
   real book depth, but whether 93 shares are simultaneously takeable on all 11 legs has not been
   verified against fills.
5. **Merge-back assumption unverified for the BUY side.** The 07-26 audit confirmed
   `convertPositions` redeems m NO tokens for (m−1) USDC immediately. The equivalent for a
   complete 11-leg YES set has **not** been checked. If it doesn't exist, only the
   hold-to-resolution column is valid.
6. **Diurnal / weekday coverage.** Single contiguous Sun→Mon window. Hit rate by hour was very
   uneven (1,077 hits in the 01:00Z hour vs 70 in 21:00Z). No weekday data at all.
7. **Episode definition is a judgment call.** 300s is arbitrary; the table above bounds it at
   $84–112/day, so it is not load-bearing, but it is a choice.
8. **Resolution-time approximation** — slug date +26h UTC. Affects only the hold-to-resolution
   capital column, never P&L.

## What is NOT in doubt (re-verified, don't re-litigate)

From the 07-26 audit, all measured against the live API: the token mapping (275/275), the
partition structure (149/149 boards), exactly-one-winner (900/900 historical), snapshot coherence
(96% single-response boards; stitch bias −0.003%), and the taker fee itself
(`{"exponent":1,"rate":0.05,"rebateRate":0.25,"takerOnly":true}` on all 1,639 markets).

**On selection there is no loss mode.** The scanner emits a row only when net-of-fee profit is
positive at depth. There is no path by which a fee-aware bot knowingly enters a loser. The
−$10 to −$16 figure in the 07-26 verdict re-priced what the *old gross-optimal* scanner had
picked; it was the bug report, not a forecast. All loss risk lives in execution (items 3 and 4).

## Next step proposed (not built)

A **shadow-fill test**: when a hit fires, immediately re-fetch all 11 books and record whether
the scored prices are still there. One extra HTTP call per hit, no capital at risk, and it
converts "$19–106/day on paper" into "$X/day we could actually have taken." That is audit
target #1, and it is cheap.
